## Public-API reproduction (real HTTP, real restarts)

The only injection is the documented CCR-13 configuration drift: quote while the
mock vault fee is **100 bps**, stop the API, restart against the **same database
and same `FP_CLAIM_SEAL_KEY`** with `FP_VAULT_FEE_BPS=50`, then fund.

1. **API at 100 bps.** `POST /v1/recipients` → **201**. `POST /v1/quotes` (PH
   crypto, PayerPays, send 100000 USD) → **201**:
   - settle `amountIn` **9,826,856,435 USDC**
   - frozen `fees.flexiPayFee` **98,268,564 USDC** (100 bps)
   - `settleUnlockedRemainder` **1 USDC**
   - `expectedReceive` **9,826,856,435 USDC**

   `POST /v1/payments` (`claim_link`, `one_off`) → **201**, payment
   `pay_d636b9811f97a094e4a4cc9a`, status `awaiting_funding`.

2. **Restart at 50 bps**, same DB and seal key. `POST /v1/payments/{id}/fund` →
   **409** `fee_drift`:

   ```
   lock fee drift: locked.fee=49134282 USDC != quoted flexiPayFee=98268564 USDC (CCR-13)
   ```

3. **After the 409**, before any replay:
   - `GET /v1/claims/{token}` → **200**, claim `open`,
     `paymentStatus: "refunded"`.
   - `POST /v1/claims/{token}/accept` (crypto_wallet, stellar, simulated) →
     **409**:

     ```
     code: settle_failed
     message: the funds for this payment were returned; the claim cannot be accepted
     ```

   The claim stays `open`; the payment stays `refunded`; no release is
   attempted.

4. **Replay in the same process.**
   - `POST …/fund` → **200**, body `status: "refunded"` (idempotent replay, no
     new lock).
   - `POST …/accept` → **409 `settle_failed`**, same message.
   - `GET /v1/payments/{id}` → refs and events unchanged.

5. **Restart again at 50 bps**, same DB and seal key.
   - `POST …/accept` → **409 `settle_failed`**.
   - `POST …/fund` → **200**, `status: "refunded"`.
   - One more fund and accept replay in that process → the same 200/409.
   - Direct DB read after the third replay: 10 events, 15 audit rows, refs
     unchanged, event snapshots deeply equal to the pre-replay read
     (`afterThird.unchanged = true`).

### Refund proof boundary (important)

The 50-bps API process that created the lock also performed the refund, in the
same in-memory mock vault (`fund` = tx1, `lock` = tx2, `refund` = tx3). The
proof of refund is the durable `releaseTxRef = mock-tx-3`, the `payment.onchain`
phase `refund` event, and `payment.refunded` — all read from the database after
two later process starts.

The mock payout itself is gone after a restart. I did **not** query the mock
vault after restart, and I do **not** treat an absent mock payout, or an
unavailable `status()` result, as proof that the refund succeeded. The
after-restart evidence is only the durable database state and the claim gate.

`npx vitest run test/orchestrator.test.ts -t "CCR-15" --reporter=verbose` → **3
passed / 8 skipped, exit 0**.

The injected vault (`countingVault({ lieAboutFee: true, refundThrows: true })`)
makes the refund throw `simulated refund outage`. The test asserts:

- settle leg `failed`, `errorCode` `fee_drift`, refs retained;
- `errorMessage` records both the drift and
  `refund failed: simulated refund outage`;
- `releaseTxRef` stays `null`;
- payment is `failed`, **not** `refunded` and **not** `paid`;
- `completeClaimSettle` throws `ClaimReleaseRefusedError`;
- replay throws `cannot fund payment in status failed`, with `lockCalls = 1` and
  `fundCalls = 1` (no re-lock).

This is evidence for CCR-15 step 4 only; it is not public-API evidence.

### Crash after lock, recovery through `findLock` — PASS

The same run's third CCR-15 test makes `lock` succeed and then throws
`simulated crash after lock`, before the refs are durable. The settle leg stays
`processing` with null refs. On replay,
`findLock(vaultPayer, paymentId, lockAttempt)` finds the real payout, detects
the vault's 50-bps drift, fails and refunds it, and does not re-lock. Final
payment `refunded`; `fund/lock/refund` counts are 1/1/1.
