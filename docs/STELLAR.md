# Stellar usage (judges / demo)

How FlexiPay uses Stellar on **testnet** in the arrival baseline. Public contract
and asset ids live in `scripts/testnet/testnet-ids.env` (generated by
`scripts/testnet/setup.sh`). Secrets stay in git-ignored
`scripts/testnet/.env.secrets` and are never pasted into docs or evidence.

Tested integrated tip for the recorded D1/D2 run: **`975d959`**. Evidence:
`scripts/demo/evidence/2026-10-23-d1-d2-final-acceptance.md`.

## What is real vs simulated

| Piece | Real on Stellar testnet? |
| --- | --- |
| `payout_vault` lock (`create_payout`), claim (`claim`), cancel (`cancel`) | **Yes**, when `FP_SETTLEMENT=stellar` |
| USDC (test) asset / SAC used by the vault | **Yes** (ids in `testnet-ids.env`) |
| Bank collect / payout, e-wallet, FX convert | **No** — simulated providers in `config/`, labelled **SIMULATED** in the UI |
| Custodial demo recipient keys | Backend-held testnet keys for the baseline demo; clearly labelled. Passkey wallet is **planned event work**, not built in the baseline |

Offline demo (`npm run demo:offline`) forces `FP_SETTLEMENT=mock`: settlement
refs look like `mock-tx-*` and do **not** prove chain activity.

## Settlement selection

`apps/api` builds the settlement adapter from `FP_SETTLEMENT` (`mock` default,
or `stellar`). Demo scripts inherit that mode from the environment;
`node scripts/demo/run-all.ts --stellar` sets `FP_SETTLEMENT=stellar` for each
child. The **API process** must already be running in the same mode.

## On-chain evidence (baseline)

Acceptance does not treat a 64-hex string as sufficient proof. For DF3/DF4 on
Stellar, lane D decodes the transaction via RPC (`scripts/demo/lib/stellar-proof.ts`):

- Lock invokes `create_payout` on the configured vault with the payment’s
  external id hash and claim hash.
- Release invokes `claim(payoutId, secret, recipient)` on the same vault; fee
  mode / principal / fee / net match the frozen quote (CCR-13).
- Refund path invokes `cancel(payoutId)`.

Recorded example hashes and payout ids are in the evidence markdown (sanitised
where needed). Prefer that file over copying hashes into the pitch.

`Leg.releaseTxRef` may hold a **release or refund** hash (CCR-12). Paid claims
are proven with `Payment.status`, settle leg status, and
`payment.onchain` `phase: "release"` — not the field name alone.

## APIs and UI

- Protected platform calls: `/v1/quotes`, `/v1/payments`, fund, events, etc.
- Public claim: `GET/POST /v1/claims/{token}` (accept).
- Local web: Vite CCR-19 proxy injects the sandbox Bearer server-side; the
  browser never holds `FP_API_KEY`.
